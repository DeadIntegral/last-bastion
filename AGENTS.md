# AI Agent Working Agreement

This file is the mandatory entry point for every AI agent working in this repository.

## Read before changing code

1. Read this file completely.
2. Read `docs/GAME_SPEC.md` for current product rules, content, architecture, and implementation status.
3. Read `docs/BALANCE.md` before changing economy, rewards, progression, combat stats, waves, or difficulty.
4. Read `README.md` for commands and player controls.
5. Inspect the affected code before proposing or applying a change.

## Documentation is part of every task

The documentation must always describe the game that actually exists in the repository.

- Update `docs/GAME_SPEC.md` in the same change whenever gameplay, balance, content, UI flow, architecture, persistence, controls, or tooling changes.
- Update `docs/BALANCE.md` in the same change whenever a currency, reward, cost, formula, stat, wave, cooldown, or difficulty value changes.
- Update `README.md` whenever installation, commands, controls, or the user-facing feature summary changes.
- Update this `AGENTS.md` when the development workflow or the obligations of future agents change.
- Record important completed changes in the changelog at the bottom of `docs/GAME_SPEC.md`.
- Do not claim a feature is implemented when it is only planned. Use the explicit status labels `Implemented`, `Partial`, and `Planned`.
- Documentation updates are part of the definition of done, not a follow-up task.

## Toolchain rules

- Use Yarn Classic. Use `yarn install`, `yarn dev`, `yarn test`, `yarn balance`, `yarn lint`, and `yarn build`.
- Do not create `package-lock.json` or use npm for project workflows.
- Use Vite 8.
- TypeScript 8 was requested, but it does not exist in the registry as of 2026-09-12. The project therefore uses the latest stable TypeScript 7.0.2. Upgrade to TypeScript 8 only after an official stable package is available and the full verification suite passes.
- Use Oxlint. Do not add ESLint or ESLint configuration.
- Use `apply_patch` for source and documentation edits.

## Product and code rules

- This is an original game. Do not copy names, art, audio, text, or other protected content from Epic War or another game.
- React owns menus and HUD. Phaser owns the battle simulation and battle rendering. Zustand owns persistent progression.
- Preserve the navigation hierarchy. With no save, the title screen contains New Game first, disabled Load, Import, and Credits. New Game resets the profile and auto-plays the four-scene illustrated CSS cinematic before entering the map without a next action; retain the visible skip and Escape shortcut, while Continue and Import bypass the opening. `src/data/opening.ts` is canonical for its ordered copy, image paths, and timing, and `public/assets/opening/README.md` records the selected project-owned WebP art and prompts. Do not replace a shot without a versioned asset and matching documentation. When browser-local progress exists, replace Load with Continue, place it first as the primary action, and keep New Game second with its reset confirmation; never make the player search past New Game to resume. The kingdom map is the in-game hub for the armory, hero hall, fortress tree, stage-unlocked facilities, achievements, codex, daily reward, mysterious merchant, and sound setting. On desktop, render these actions in a compact vertical operations panel outside the map/content column; on narrow screens, collapse them into a compact toolbar above—not over—the map. Beast challenges are discoverable map-rift nodes and must never return to a separate menu or the operations panel. Keep readable primary and secondary labels while minimizing button area. Progression screens and battle results return to the map; only the map and Credits return to the title.
- Keep balance and content definitions in `src/data`; do not scatter values through React components.
- Treat soldiers, heroes, enemies, bosses, stages, first-clear rewards, achievements, and codex records as structured data. Every new combatant must receive a matching codex entry and a clear unlock or encounter rule.
- Preserve the counteroffensive setting: the kingdom begins one step from total conquest and advances from the Last Bastion through traitorous human armies, goblins, orcs, ogres and other monsters, bound spirits, and demons toward the Demon King's seat. Current UI and content call giant hostile bosses `마수`, never `거신`.
- Soldier definitions are faction-neutral and canonical in `troopDefinitions`. Both player summons and enemy waves must use the same base definition; never create a player-only or enemy-only stat copy of the same troop.
- The implemented shared roster contains exactly 50 troops grouped by `unitFamilyById`: kingdom, betrayer, goblin, orc, ogre, beast, spirit, and demon. It explicitly includes Griffin Rider, Kingdom Mage, Archmage, and Ifrit. Every roster member must remain covered by codex, mastery, art-or-procedural presentation, and a campaign encounter, direct grant, fortress recruit, or challenge acquisition path. Keep the progression-path regression test when changing the roster.
- Preserve the shared character-art contract. `src/data/characterArt.ts` is the only ID-to-sheet/frame or procedural-fallback mapping; React and Phaser must consume it rather than duplicating presentation choices. Enemy troops use the same canonical art. Every runtime atlas is 612 × 640 and divisible into sixteen 153 × 160 cells. Retain source images and generation records under `public/assets/characters`, add a new sheet instead of changing frame geometry when capacity is exhausted, and add coverage whenever the roster changes. Rebuild `expansion-atlas.png` only through `yarn art:atlas`; the script must keep true alpha in used and empty cells, and opaque black frame backgrounds are a regression.
- Preserve localized attack motion for every troop, hero, and boss. The current atlases are transparent single-pose PNG frames, not skeletal assets; `src/game/combatMotion.ts` therefore assigns slash, thrust, shoot, cast, crush, or lunge rigs and writes into a spawn-time pose object. Keep the portrait/body, shadow, health bar, and enclosing combatant container stable during attacks; animate only the attached arm/weapon/effect rig. Create rig objects once per combatant and do not allocate Phaser objects, tweens, timers, or pose objects per strike. A future true articulated or frame-by-frame replacement requires new separated-part or multi-frame source art rather than merely changing PNG to another extension.
- Preserve data-driven deployment sizes and attack patterns. Command/cooldown and mastery counts apply once per deployment, while both player and enemy deployments expand the same `squadSize`. Pierce must respect its two/three-target cap and forward continuation distance; melee cleave hits every valid target in normal range. New patterns must work symmetrically for both sides and explicitly handle flying targets.
- Preserve symmetric rear-fortress deployment. Player soldiers and heroes spawn/respawn 50 units behind the player fortress and enemy wave/reinforcement soldiers spawn 50 units behind the enemy fortress, with 16-unit rearward squad spacing from `fortressDeploymentTuning`. While a fortress lives, opposing units cannot directly select combatants still behind it; ranged defenders may fire from cover and melee defenders advance through the fortress line. Destroying the enemy fortress removes that targeting shield. Campaign bosses and named elite guards remain authored in front, and fortress-less challenges must not invent an enemy shield.
- Preserve `maxActivePerSide` as a data-driven living-body limit for exceptional beasts, spirits, and top-tier summons. Enforce it for player cards, scripted enemy waves, and reinforcements without faction exceptions or overflow from the equipment deployment capstone. The battle HUD must show current/maximum occupancy, and progression screens must disclose the limit before deployment.
- Preserve the Archer/Crossbow role boundary for both factions. The two-body Archer must clearly outrange the tougher one-body Crossbow and win in combined single-target deployment pressure; the slower, harder-hitting Crossbow may surpass it only through a lined-up two-target pierce and must never pierce three soldier targets. Cover these inequalities in tests whenever either unit changes.
- Campaign difficulty must modify shared troops through the stage-level equipment-only `enemyUpgrades` profile. Prefer recombining shared troops and bounded equipment profiles over duplicating nearly identical combatant data.
- Every stage declares `enemyFaction` and a structured `terrain`. Apply terrain HP, attack, and movement multipliers to all computer-controlled combatants in that encounter and include them in the offline difficulty estimator. Never bake a challenge terrain bonus into the recruitable base definition. Current beast-only challenges visibly use HP ×10 and ATK ×2.5 terrain; changing that contract requires matching UI, tests, and balance documentation.
- Enemy soldiers and bosses must never receive mastery levels or mastery XP. Their only generic stat progression is weapon, armor, and boots equipment, each capped at rank 5; later difficulty comes from formations, reinforcement pressure, advanced-unit mechanics, objectives, and boss patterns. Cover the equipment cap and late living-enemy caps in tests.
- Treat new enemy mechanics as a separate difficulty axis. Keep advanced-unit introduction milestones structured and regression-tested: stage 7 after the regional boss is a familiar-roster recovery stage, Royal Cavalry first appears partway through stage 8, stage 9 reinforces that lesson, exactly one strengthened Griffin Rider first appears late in stage 10, and stage 11 combines Cavalry with two Griffins. Griffin is a rare top-tier flying assault unit and must not enter continuous reinforcement rotations. Do not move or mass a signature threat earlier without a deliberate balance revision and documentation update.
- The campaign contains 30 stages split into five six-stage map regions. Clearing campaign boss sieges 6/12/18/24 reveals the next region, while stage 30 is the finale. Campaign stages marked `boss` retain an enemy fortress, a small slow alive-capped low-tier garrison, and require both the boss and fortress to be destroyed. Destroying the fortress must stop further garrison production. Boss-only encounters belong in the separate `challengeStages` roster, never in `stages`, and retain no fortress, waves, or reinforcement. Derive final-stage limits from `stages.length` and combat behavior from `boss`/`challenge` metadata rather than hardcoding one final stage.
- Render each unlocked `challengeStages` entry as a distinct pulsing rift node inside the horizontally draggable campaign world, near its required campaign milestone. Selecting it must reuse the map mission panel for terrain multipliers, first-clear reward, repeat reward, and deployment; locked challenges remain undiscovered rather than appearing in a separate roster.
- Preserve the capped fortress distance curve: campaign stage 1 starts at 1,050 virtual units, each next stage adds 25 until stage 15 reaches the 1,390 cap, and stages 16–30 retain that maximum instead of stretching progression artificially. With the player fortress at X 105, the first enemy fortress is at X 1,155. Both rendering and spawning must use the resolved stage distance rather than a fixed enemy-fortress coordinate.
- Preserve pointer-based horizontal map dragging for mouse, pen, and touch. Do not capture the pointer on press: capture only after the drag threshold so stage buttons retain ordinary clicks. A completed drag must suppress its following synthetic click, while a short pointer action and keyboard activation must continue to select nodes normally. Keep native scrollbar access and vertical page touch scrolling available.
- Every non-boss stage must define finite opening waves and a continuous, alive-capped reinforcement pattern. Campaign boss sieges instead require the documented low-tier fortress garrison. Do not allow the enemy army to stop producing merely because the opening timeline ended; only a destroyed producing fortress ends boss-garrison reinforcement.
- Named elite defenders must reuse a canonical troop plus the stage's explicit `eliteGuard` modifiers. Keep them single-body, show their identity on the map, and do not expose enemy equipment ranks or elite numeric modifiers there.
- Encountered non-boss troops become recruit candidates. Tier-signature royal troops may instead become candidates directly through fortress promotion when their definition sets `requiresEncounter: false`. Recruitment grants the exact shared troop, and acquired troops can be placed in a persistent battle formation of one to four troop types. Enforce both acquisition paths in the store, not only the UI.
- Troops marked `recruitSource: 'challenge'` cannot be purchased through ordinary encounter recruitment. Current challenge-only recruits are Ogre Crusher, Storm Spirit, Hellhound, and Ifrit. A first challenge clear grants the exact shared base troop once, persists in `clearedChallenges`, never advances campaign progress, and removes all challenge-only terrain and boss modifiers when the troop is used by the player.
- Preserve explicit movement-domain combat rules. Units tagged `flying` move above the ground lane and cannot be targeted by non-ranged combatants or ground-only area attacks; ranged troops and heroes plus the fortress watchtower can target them. Any new attack type must deliberately declare or implement whether it can affect flying targets.
- The war codex shows only troops the player has acquired or encountered, acquired heroes, and encountered bosses. A troop that is both acquired and encountered counts once. Do not reveal undiscovered names, descriptions, silhouettes, or statistics.
- Keep stage first-clear rewards data-driven and grant them only once per save. Any new reward type needs persistence, result-screen feedback, and specification updates.
- Feature unlocks may be attached to structured first-clear rewards. Their availability must derive from the corresponding cleared-stage record or another explicit persisted source and must be enforced in the store, not only by a disabled UI button. The current stage-9 `hero-training` facility converts only Gold into mastery XP through the packages in `src/data/features.ts`, applies only to recruited heroes, clamps at level 30, and never replaces battle-earned XP.
- Preserve the player's two-track character progression model: gold buys equipment levels, while repeated battle use grants free mastery XP. Do not turn player mastery into a paid upgrade or apply it to computer-controlled forces.
- Preserve the shared healer contract. `priest` is the canonical faction-neutral healer: it heals the most injured living ally in range before attacking, uses the same healing behavior for player and computer forces, and scales healing through the same weapon/mastery flat gains. Healing support must remain represented in the offline threat estimator.
- Soldier mastery caps at level 50. The implemented hero roster contains Edric, Selene, Ria, Mirena, and Bran. Hero mastery caps at level 30 and derives three awakenings at levels 10, 20, and 30 without adding persistence fields; every awakening applies the character-specific fixed active-power bonus, reduces active cooldown by 1.5 seconds, and increases the hero's data-driven nearby-allied aura. Keep the cap, milestones, combat values, aura range/effect, hall display, and tests synchronized.
- Preserve the independent weapon, armor, and boots equipment branches for each soldier and hero; do not collapse them back into one upgrade level.
- Equipment progression uses role-specific absolute gains stored on each canonical combatant definition. Usage mastery is also an absolute, character-specific HP/ATK growth track stored in `src/data/mastery.ts`; do not restore a shared percentage curve. Hero mastery additionally strengthens active-skill power and reduces respawn time up to its per-hero cap.
- Preserve the non-stacking soldier equipment capstone: completing any one equipment branch at rank 5 grants +1 body per deployment to both player and stage-equipped regular troops. Derive the displayed and spawned squad size from the trained definition; heroes, bosses, and named single-body elites are excluded.
- Preserve the three-branch fortress tree: economy, defense, and artillery. It has three persistent fortress tiers, tier-gated recruitment permits, eighteen five-rank nodes, and data-driven promotion requirements. `전리품 회계` scales only battle and first-clear Gold, while `왕립 야전 교범` scales only battle-earned soldier/hero mastery XP; neither scales achievement rewards, daily rewards, or paid Hero Training packages. New fortress effects must have data definitions, persistence, battle integration, tests, and specification updates; never unlock a gated recruit in UI only without enforcing the tier in the store.
- Soldier Command-cost research must use the shared `soldierCommandCost` calculation for affordability checks, actual Command deduction, and HUD display so those values cannot diverge. Costs round up to whole Command and never fall below 10.
- Preserve the battle-only `전시 동원령`: it can fire only at 100% of the current Command maximum, consumes all Command, grants +25 maximum Command and +1.5 Command/s, and caps at three uses per battle. Keep its visible `E` control, exact simulation check, HUD state, and structured tuning synchronized.
- Preserve `Q` as the displayed primary hero-skill hotkey and `Space` as its compatibility shortcut. Any control change must update the visible HUD hint, accessible label, tests, game specification, and README together.
- Preserve the soldier summon cooldown as an animated inactive-to-active card wipe without a visible numeric countdown. Keep the exact remaining time in the accessible button label, derive progress from the fortress-modified cooldown, and retain a clear ready transition.
- Fortress requirements are entry gates, not revocation rules. A node with at least one saved rank stays upgradeable if later data adds or changes its prerequisite. During persistence merge, recover at least the highest fortress tier required by any already-researched node so older or inconsistent saves never relock paid progress.
- Fortress technology cards with prerequisites must show the prerequisite name, required rank, and player's current rank. A locked action must never reduce this to an ambiguous name-only message.
- Render fortress research as a real prerequisite tree derived from `castleTechDefinitions`, `castleTechRoots`, and `castleTechChildren`. Do not maintain a separate hardcoded visual order or connector map; desktop and mobile must retain horizontal access to deep branches. Preserve pointer-based grab-to-scroll on every branch, capture only after the drag threshold, suppress the following synthetic click, and keep short clicks, keyboard actions, vertical touch scrolling, and native scrollbars available.
- Achievement criteria derive from persistent battle statistics. Add a tracked statistic before adding an achievement that depends on it.
- Preserve the two achievement presentation modes. `묶음 보기` is the default and groups milestones by their tracked `metric`, rendering one stacked card per series; it must prioritize the earliest unlocked/unclaimed reward, then the next locked target, then the final completed step. `전체 보기` must remain available to expose every individual definition. Claiming from a stack must advance that stack without hiding another claimable reward, and grouping must stay derived from achievement data rather than a duplicated UI list.
- Keep the 64 implemented achievements organized as twelve statistic-derived series. Add milestones to those series without duplicating grouping metadata in React, preserve all existing IDs for save compatibility, and update the exact reward ladders in `docs/BALANCE.md` whenever the definitions change.
- Keep deterministic calculations in testable pure functions under `src/game` where practical.
- Treat `src/game/difficulty.ts` and `yarn balance` as the campaign difficulty and troop-efficiency gates. The estimator must derive pressure from live combat/stage data. Do not reintroduce a hand-authored difficulty number that merely duplicates the stage ID. The map must use `stageDifficultyPresentation` to convert analyzed objective, battlefield, army, reinforcement, elite, and boss pressure into the five player-facing tiers. This map tier is absolute encounter pressure, not a personalized prediction. The same command runs the roster audit: base troop cost must not exceed the base 200 Command cap, and every troop costing at least 150 must retain estimated deployment threat per Command of at least 1.0. It also runs `scripts/progression-power.test.ts`, which stress-tests a no-repeat, no-achievement, single-branch gold rush and must continue to disclose any progression cliff rather than being mistaken for a passing curve gate. Current characterized risk: Militia weapon +5 is affordable before stage 4 and flattens the stage-3-to-4 relative-pressure step to about 1.01. Run the separate audits after any unit, squad, attack-pattern, wave, reinforcement, elite, boss, objective, reward, equipment-price, or capstone change. Fix the data or justify and document a model revision; do not merely weaken thresholds to make a regression pass. Keep the audits separate from the production build.
- Keep shared boss combat parameters in structured data rather than duplicating phase thresholds, stomp values, or phase multipliers inside the battle scene. Boss stage training must scale basic attacks, HP, and attack-derived abilities together.
- Frame-dependent movement, resource generation, attacks, cooldowns, and respawns are forbidden. Use elapsed time.
- Preserve bounded high-frequency battle effects. Basic strikes, projectiles, and deployment flashes must reuse the fixed scene pools; hit flashes and attack pulses stay on combatant timer fields. Do not reintroduce per-hit Phaser object, delayed-call, or tween allocation without profiling and updating the performance contract.
- Preserve compatible saved data. When persistence changes, provide defaults or migration behavior for older saves.
- Save imports may accept either a raw profile object or the Zustand `{ state, version }` wrapper. Treat imported JSON as untrusted: whitelist persisted fields, clamp numeric ranks and resources, discard unknown combatant and achievement IDs, preserve store actions, and reject unrelated or malformed JSON.
- Royal Gems are currently earned only from the local-calendar daily reward and claimed achievements; payment, recharge, and exchange remain unimplemented. Their implemented sink is the permanent 200-Gem battle-speed license sold by the mysterious merchant revealed after clearing campaign stage 6. The operations panel opens the shop and must not perform the purchase directly. Preserve `battleSpeedUnlocked` as the entitlement and `battleSpeed` as the persisted 1×/1.5× preference. A future verified cash purchase may grant the same entitlement immediately without the stage gate, but never simulate or trust a client-only payment by inference.
- The 1.5× setting must scale the complete battle simulation consistently: movement, attack cadence, spawn schedule, reinforcements, Command regeneration, cooldowns, respawns, boss phases/stomps, elapsed battle time, timer events, and combat tweens. It must not recreate the Phaser game when toggled. Music pitch/tempo remains unchanged, while naturally more frequent combat events may trigger more sound effects.
- Preserve the production chunk boundaries: the initial app, React/Zustand vendor code, lazy battle UI, and Phaser vendor runtime remain separately emitted. Phaser is a single large upstream module and must stay outside the initial app chunk.
- Maintain usable layouts for desktop and mobile browsers.
- Load Pretendard Variable at runtime from the documented CDN URL. Do not install or bundle a Pretendard font package unless the user changes this requirement.
- Preserve the app-level procedural Web Audio engine and its menu, battle, victory, and defeat music scenes plus synthesized combat effects. Audio must start only after a browser-approved user gesture, follow the single persisted mute setting, and pause on hidden pages. Phaser audio stays disabled unless audio ownership is deliberately migrated and documented.
- Avoid expanding scope into accounts, payments, advertising, multiplayer, chat, or server persistence unless the user explicitly requests it.

## Definition of done

Before handing off a code change:

1. Run `yarn lint`.
2. Run `yarn test`.
3. Run `yarn balance` when combat or campaign balance changed.
4. Run `yarn build`.
5. Exercise the affected player flow in a browser when a browser is available.
6. Update `docs/GAME_SPEC.md` and any other affected documentation.
7. Update `docs/BALANCE.md` when balance values changed.
8. Report what was verified and what could not be verified.

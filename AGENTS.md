# AI Agent Working Agreement

This file is the mandatory entry point for every AI agent working in this repository.

## Read before changing code

1. Read this file completely.
2. Read `docs/GAME_SPEC.md` for current product rules, content, architecture, and implementation status.
3. Read `docs/BALANCE.md` before changing economy, rewards, progression, combat stats, waves, or difficulty.
4. Read `docs/FUTURE_SYSTEMS.md` before implementing or revising planned game systems. Planned entries are not current behavior until their full acceptance criteria ship.
5. Read `README.md` for commands and player controls.
6. Inspect the affected code before proposing or applying a change.

## Documentation is part of every task

The documentation must always describe the game that actually exists in the repository.

- Update `docs/GAME_SPEC.md` in the same change whenever gameplay, balance, content, UI flow, architecture, persistence, controls, or tooling changes.
- Update `docs/BALANCE.md` in the same change whenever a currency, reward, cost, formula, stat, wave, cooldown, or difficulty value changes.
- Update `docs/FUTURE_SYSTEMS.md` whenever a planned system is added, revised, partially implemented, completed, or removed. Move completed authoritative behavior into `docs/GAME_SPEC.md` and keep status labels accurate.
- Update `README.md` whenever installation, commands, controls, or the user-facing feature summary changes.
- Update this `AGENTS.md` when the development workflow or the obligations of future agents change.
- Record important completed changes in the changelog at the bottom of `docs/GAME_SPEC.md`.
- Do not claim a feature is implemented when it is only planned. Use the explicit status labels `Implemented`, `Partial`, and `Planned`.
- Documentation updates are part of the definition of done, not a follow-up task.

## Toolchain rules

- Use Yarn Classic. Use `yarn install`, `yarn dev`, `yarn test`, `yarn balance`, `yarn lint`, and `yarn build`.
- Do not create `package-lock.json` or use npm for project workflows.
- Use Vite 8.
- TypeScript 8 was requested, but it does not exist in the registry as of 2026-09-12. The project therefore uses the latest stable TypeScript 7.0.2. Upgrade to TypeScript 8 only after an official stable package is available and the full verification suite passes.
- Use Oxlint. Do not add ESLint or ESLint configuration.
- Use `apply_patch` for source and documentation edits.
- Preserve `.github/workflows/auto-assign-pr-author.yml` as metadata-only PR automation. It may use `pull_request_target` to assign the PR author, but it must keep explicit least-privilege permissions, pin third-party actions to a full commit SHA, and never check out or execute pull-request code in that privileged workflow.

Keep these rules symmetric and include their opportunity cost in the difficulty estimator. Do not reintroduce per-hit Phaser object, delayed-call, or tween allocation without profiling and updating the performance contract.
- Preserve compatible saved data. When persistence changes, provide defaults or migration behavior for older saves.
- Preserve the three-slot save contract in `src/game/saveSlots.ts`. The old single `last-bastion-profile-v1` save migrates once into slot 1, each later slot remains independent, deleting the active slot clears its active marker, and every active-profile mutation is mirrored into that slot. Never strand an old save during a storage revision.
- New portable exports must be password-encrypted with Web Crypto AES-256-GCM, a unique 16-byte salt and 12-byte IV, PBKDF2-SHA-256 with 210,000 iterations, Base64 binary encoding, and an explicit SHA-256 ciphertext checksum. The envelope must include `gameVersion` and `saveSchemaVersion`; keep those concepts separate and source the current values from `src/data/version.ts`. Never store or infer the export password. Local browser slots may remain origin-scoped automatic saves because bundling a recoverable client-side key would not provide meaningful secrecy.
- Imports must accept the current encrypted envelope plus the previous plaintext portable export, a raw profile object, and the Zustand `{ state, version }` wrapper. Treat every import as untrusted: cap file/KDF work, verify checksum before PBKDF2, require AES-GCM authentication, whitelist persisted fields, clamp numeric ranks and resources, discard unknown combatant and achievement IDs, preserve store actions, and reject unrelated or malformed JSON.
- Use the shared accessible in-game modal for confirmations and blocking notices. Do not reintroduce browser `alert`, `confirm`, or `prompt`; destructive actions must describe what will be lost, focus a safe action first, close with Escape, and keep keyboard focus inside the open dialog.

## Test strategy

- Add only the smallest regression coverage needed to protect behavior with a meaningful failure cost: combat and economy formulas, persistence/migration/security boundaries, data invariants, accessibility-critical interactions, and previously observed bugs.
- Prefer one table-driven pure-function test over several UI tests that repeat the same rule. Extend an existing focused test when it already owns the behavior.
- Do not test CSS shape, exact decorative markup, implementation-only class names, static copy, or framework behavior unless it is an accessibility contract or a proven regression. Verify presentation changes in the browser instead.
- Avoid broad snapshots and exhaustive permutations. Test representative boundaries and one integration path; let type checking, structured-data audits, and browser verification cover the rest.
- A planned document's acceptance criteria are product conditions, not a demand for one automated test per bullet. During implementation, select the minimum set that proves the distinct rules.
- Removing redundant or brittle tests is encouraged when equivalent lower-level coverage exists. Never weaken a unique safety, save-compatibility, balance, or combat-rule guard merely to reduce the test count.
- Royal Gems are currently earned only from the local-calendar daily reward and claimed achievements; payment, recharge, and exchange remain unimplemented. Their implemented sinks are the permanent 200-Gem battle-speed license revealed after stage 6 and three sequential formation-slot licenses costing 150/250/350 Gems after stages 12/18/24, all sold by the mysterious merchant. The operations panel opens the shop and must not perform purchases directly. Preserve `battleSpeedUnlocked`, `battleSpeed`, and clamped `formationSlotPurchases` as persisted entitlements/preferences; migrate the legacy `formationSlotUnlocked: true` field to one purchase. A future server-verified Quick Starter may grant Gems, speed, and exactly the first formation purchase without stage gates, but never simulate or trust a client-only payment by inference.
- The 1.5× setting must scale the complete battle simulation consistently: movement, attack cadence, spawn schedule, reinforcements, Command regeneration, cooldowns, respawns, boss phases/stomps, elapsed battle time, timer events, and combat tweens. It must not recreate the Phaser game when toggled. Music pitch/tempo remains unchanged, while naturally more frequent combat events may trigger more sound effects.
- Preserve the production chunk boundaries: the initial app, React/Zustand vendor code, lazy battle UI, and Phaser vendor runtime remain separately emitted. Phaser is a single large upstream module and must stay outside the initial app chunk.
- Maintain usable layouts for desktop and mobile browsers.
- Load Pretendard Variable at runtime from the documented CDN URL. Do not install or bundle a Pretendard font package unless the user changes this requirement.
- Preserve the app-level procedural Web Audio engine and its menu, battle, victory, and defeat music scenes plus synthesized combat effects. Audio must start only after a browser-approved user gesture, follow the single persisted mute setting, and pause on hidden pages. Phaser audio stays disabled unless audio ownership is deliberately migrated and documented.
- Avoid expanding scope into accounts, payments, advertising, multiplayer, chat, or server persistence unless the user explicitly requests it.

## Definition of done

Before handing off a code change:

1. Run `yarn lint`.
2. Run `yarn test`.
3. Run `yarn balance` when combat or campaign balance changed.
4. Run `yarn build`.
5. Exercise the affected player flow in a browser when a browser is available.
6. Update `docs/GAME_SPEC.md` and any other affected documentation.
7. Update `docs/BALANCE.md` when balance values changed.
8. Report what was verified and what could not be verified.

# 엔지니어링 보조 리뷰와 AI agent 작업 명세

검토일: 2026-09-27

콘텐츠·이미지·애니메이션·게임 경험의 주 리뷰는 [IMPROVEMENT_REVIEW.md](IMPROVEMENT_REVIEW.md)다. 이 문서는 최초 리뷰의 기술 안정성 항목을 보존한 보조 자료이며 전체 제작 우선순위를 대신하지 않는다.

이 문서는 현재 코드에 대한 소프트웨어 엔지니어링·게임 UX 리뷰다. 개선 구현은 하지 않았으며 아래 작업의 상태는 모두 **Planned**다. 현재 게임 규칙은 `GAME_SPEC.md`, 수치는 `BALANCE.md`, 계획의 상태 관리는 `FUTURE_SYSTEMS.md`를 따른다. 본 문서의 제안은 현재 동작으로 간주하지 않는다.

## 검토 범위와 판단 기준

- 확인: 저장/불러오기, 전투 진입과 결과 처리, HUD와 입력, 모달, 진행 구조, 기존 테스트 및 명세.
- 실행: `yarn lint`, `yarn test`(22개 파일·143개 테스트), `yarn balance`(3개 테스트), `yarn build` 모두 통과.
- 미실시: 실제 브라우저 플레이, 모바일 실기기, 스크린리더, 네트워크 장애 주입, 전체 캠페인 클리어, FPS/메모리 측정. 따라서 체감 난이도나 화면 불편을 재현 완료라고 주장하지 않는다.
- **코드 확인**: 구현에서 직접 확인한 구조·누락. 실제 사용자 피해 발생을 재현했다는 뜻은 아니다.
- **개선 가설**: 플레이 또는 측정으로 효과를 확인한 후 구현 범위를 정할 항목.
- P1: 저장 손실 또는 핵심 흐름 복구. P2: 플레이 이해·접근성·품질 신뢰. P3: 유지보수 비용. 이번 검토에서 재현된 P0 장애는 없다.

공유 병종, 구조화된 데이터, 순수 전투 판정, 효과 풀, 분리된 밸런스 검사, 구버전 저장 호환성은 이미 갖춰져 있다. 이 장점을 유지하면서 실패 상황과 플레이어 피드백을 보강하는 것이 우선이다. 테스트 통과만으로 저장 경쟁이나 실제 전투 재미가 검증되지는 않는다.

## REV-01 — 다중 탭 저장 슬롯 오염 방지

**문제와 근거:** `src/game/saveSlots.ts`의 `writeActiveSaveSlot()`은 매번 localStorage의 공용 active-slot 키를 다시 읽는다. `src/store/useGameStore.ts`의 구독은 그 대상에 현재 탭의 메모리 상태를 저장한다. 탭 A가 슬롯 1을 연 뒤 탭 B가 슬롯 2를 열면, A의 다음 강화·음소거 등 상태 변경도 슬롯 2에 기록될 수 있다. 현재 `storage` 이벤트 기반 충돌 처리가 없다.

**재현 절차:** 동일 origin의 두 탭에서 서로 다른 내용의 슬롯 1/2를 연다. A에서 금화를 소비하거나 음소거를 변경한 뒤 슬롯 2 원문과 요약을 비교한다. 실제 사용자 저장 대신 격리된 테스트 프로필을 사용한다.

**구현 범위:** 활성 세션의 슬롯 ID를 탭 단위로 고정하고, 공유 마커는 마지막 선택 복원 용도로 분리한다. 같은 슬롯을 동시에 연 경우도 revision 충돌 또는 명시적 쓰기 소유권으로 감지한다. 단순히 두 탭의 데이터를 합산하지 않는다.

**완료 조건:** 다른 슬롯을 연 탭의 쓰기·삭제가 원래 탭의 저장 대상을 바꾸지 않는다. 같은 슬롯의 오래된 상태는 조용히 덮어쓰지 않고 복구/다시 불러오기 선택을 제공한다. 기존 세 슬롯·단일 저장 이전·내보내기 호환성을 유지한다.

**검증:** 서로 다른 두 슬롯과 같은 슬롯의 경쟁을 대표 사례로 테스트하고 두 탭에서 확인한다. 메타데이터 추가 시 기본값과 마이그레이션을 문서화한다. 관련 파일: `saveSlots.ts`, `useGameStore.ts`, `App.tsx`의 MainMenu.

## REV-02 — 저장 실패 감지와 복구

**문제와 근거:** `storageAvailable()`은 존재 여부만 검사한다. `initializeSaveSlots()`는 store 모듈 로드 시 실행되고, get/set/remove의 예외 처리가 없다. 접근 제한이나 용량 초과가 발생하면 부팅·상태 변경이 예외로 끝날 수 있다. `importSave()`의 catch는 저장 실패도 형식 오류처럼 반환할 수 있으며, 이미 바뀐 메모리 상태와 파일 상태를 구분하지 않는다.

**구현 범위:** 저장 접근을 공통 어댑터로 모으고 읽기 실패/쓰기 실패/잘못된 파일을 구분한다. 플레이 상태와 마지막으로 저장에 성공한 상태를 식별하고 저장되지 않았음을 알린다. 메모리 상태를 파일로 내보내는 복구 경로를 제공한다. 신규 import는 검증 후 대상 슬롯에 안전하게 반영한다.

**완료 조건:** 실패해도 흰 화면이나 정상 저장 성공 안내가 나오지 않는다. 기존 슬롯과 마이그레이션 원본을 보존한다. 실패한 덮어쓰기에서 기존 데이터와 활성 상태를 잃지 않는다. 재시도 또는 내보내기로 빠져나갈 수 있다. 언어 설정 등 별도 localStorage 접근도 동일 장애에 안전한지 확인한다.

**검증:** getItem 접근 예외, setItem 용량 초과, 이전 도중 쓰기 실패를 주입한 최소 회귀 테스트. 정상 현재/구형 import 경로도 한 번 확인. 스키마 변경이 있으면 구버전 기본값 명시.

## REV-03 — 전투 결과를 한 번에 확정

**문제와 근거:** `App.tsx`의 `handleResult()`는 `addReward` → `completeStage`/`completeChallenge` → `recordBattle`을 따로 호출한다. 각 상태 변경마다 슬롯이 저장되므로 중간 실패 시 금화·클리어·숙련·통계가 일부만 반영될 수 있다. `BattleScene.finish()`의 `ended`는 같은 scene의 중복 발행을 막지만 store의 결과 확정 경계는 아니다.

**구현 범위:** store에서 전투 결과와 모든 파생 보상을 계산한 뒤 하나의 다음 프로필로 반영하는 action으로 통합한다. 활성 전투의 식별자와 이미 처리한 결과를 구별해 동일 결과를 중복 반영하지 않는다. 서버나 결제 검증으로 범위를 넓히지 않는다.

**완료 조건:** 승리·패배·도전 결과가 각각 일관된 프로필로 확정된다. 같은 결과를 재전달해도 두 번 지급하지 않는다. 정상 재도전 승리는 별개 전투로 보상받는다. 이탈은 이 action을 호출하지 않으며 어떤 진행도 기록하지 않는다. 저장 실패 정책은 REV-02를 따른다.

**검증:** 중복 결과, 도전 최초/반복 클리어, 확정 중 저장 실패, 이탈 무기록을 최소 대표 사례로 확인. 결과 화면에는 실제 확정된 보상을 전달한다. 수치 변경 없이 기존 보상 계산을 보존한다.

## REV-04 — 전투 로딩 실패에서 복귀

**문제와 근거:** `App.tsx`는 lazy `BattleView`에 Suspense 로딩 화면만 둔다. `src/main.tsx`에도 오류 경계가 없고, `BattleScene.preload()`에는 에셋 실패를 React에 전달하는 흐름이 없다. 청크 다운로드 실패나 필수 에셋 실패에 대한 사용자의 복구 경로가 부족하다. 프로덕션 Phaser 청크는 약 1,197 kB, gzip 약 319 kB지만 이것만으로 성능 불량이라고 단정하지 않는다.

**구현 범위:** React 청크 실패와 Phaser 준비/실패 상태를 구분하고, 재시도·지도로 복귀를 제공한다. 필수 이미지 누락은 명시적으로 처리하며 잘못된 상태에서 전투를 시작하지 않는다. 실패/재시도 시 이벤트와 Phaser 인스턴스를 정리한다.

**완료 조건:** 느린 로딩은 준비 상태로 보이고, 실패하면 무한 대기하지 않는다. 재시도가 실패해도 복귀가 가능하다. 지도 복귀는 패배나 이탈 보상을 만들지 않는다. 초기 앱과 Phaser의 기존 청크 분리를 유지한다.

**검증:** production preview에서 전투 청크 요청 차단, atlas 요청 실패, 정상 재진입을 확인한다. 필요한 오류 전파 테스트 하나를 추가한다. 배포 환경 전체 새로고침이 필요하다면 저장 성공 여부를 먼저 확인한다.

## REV-05 — 일시정지와 상태 안내 접근성

**문제와 근거:** `BattleView.tsx`의 일시정지는 일반 div와 버튼이며 대화상자 의미·진입 포커스·포커스 순환 처리가 없다. 이탈 확인만 `GameModal`을 사용한다. 하단 live region은 영웅 쿨다운 초 단위 변화를 계속 알린다. 공용 모달은 포커스 순환을 구현하지만 배경을 inert 처리하지 않는다.

**구현 범위:** 일시정지부터 이탈 확인까지 포커스 소유권을 일관되게 만든다. 재개 후 적절한 컨트롤로 돌아오게 하고 배경 조작을 막는다. live region은 사용 가능 전환 등 의미 있는 변화 중심으로 조정한다. 탭 비활성화 시 실제 전투 정지/복귀 정책도 브라우저에서 확인해 명세에 기록한다. 현재 자동 재개 피해가 재현된 것은 아니다.

**완료 조건:** 키보드만으로 정지→이탈 취소→재개가 가능하고 보이지 않는 배경으로 포커스가 새지 않는다. Q/Space/R/Escape의 기존 역할과 물리 코드 규칙을 지킨다. 스크린리더가 초마다 반복 안내하느라 주요 정보를 놓치지 않는다. 보조기술용 정확한 소환 쿨다운 레이블은 유지한다.

**검증:** 포커스 이동/복원 대표 통합 테스트와 키보드·스크린리더 수동 검증. 게임 수치·영속 필드 변경 불필요.

## REV-06 — 초반 전술 학습 안내

**관찰과 가설:** 오프닝은 세계관을 설명하고 HUD는 단축키를 제공한다. 그러나 현재 전투/화면 코드에는 플레이 행동에 반응하는 단계별 학습 흐름이 없다. 신규 플레이어가 지휘력 회복, 전열과 궁수, 공중 표적, 성채+보스 이중 목표를 이해하는지는 검증되지 않았다.

**먼저 할 일:** 신규 저장으로 1~3장, 첫 보스, 첫 공중 위협을 관찰하고 실패 지점을 기록한다. 단순히 메뉴를 모두 설명하는 강제 튜토리얼을 만들지 않는다.

**구현 범위:** 확인된 혼란만 대상으로 짧은 상황 안내를 구조화된 데이터에 정의한다. 건너뛰기·다시 보기 가능, 마우스/터치/키보드 모두 지원. 안내는 React가 소유하고 전투 관찰은 이벤트 경계를 사용한다. 적에게 튜토리얼 보정을 추가하지 않는다.

**완료 조건:** 필수 조작을 안내 때문에 막지 않고, Continue/import 사용자에게 강제 오프닝을 재생하지 않는다. 미발견 병종·정확한 숨김 수치를 누설하지 않는다. 안내 완료를 저장한다면 슬롯별 기본값과 구형 저장 정책을 둔다.

**검증:** 관찰된 혼란과 개선 후 수행 결과를 기록한다. 자동 테스트는 실제 도입한 상태 전환·건너뛰기 경계만 보호한다. 수치 조정은 별도 밸런스 작업이다.

## REV-07 — 결과에서 다음 전략을 판단할 정보

**문제와 근거:** `ResultScreen`은 시간·처치·손실·골드, 숙련 XP, 업적과 최초 보상을 보여 준다. 패배 문구는 고정되어 있고 병종별 역할 기여나 숙련 레벨의 전후 변화는 제공하지 않는다. 플레이어가 실패 이유를 이해하는 데 충분한지는 검증이 필요하다.

**구현 범위:** 먼저 기존 데이터로 숙련 레벨 상승과 새로 열린 기능을 요약한다. 전투 분석이 필요하면 병종별 피해·치유·생존 기여 중 의사결정에 필요한 최소 집계만 battle-local 데이터로 수집한다. 관측하지 않은 패배 원인을 단정하지 않는다.

**완료 조건:** 다음에 편성/장비 중 무엇을 검토할지 근거를 보여 준다. 치유·보호 역할을 피해량만으로 낮게 평가하지 않는다. 결과에서 기본 복귀는 지도이며 별도 시설 직행으로 탐색 계층을 바꾸지 않는다. 분석 집계를 저장·업적 조건으로 사용하지 않는 한 영속 필드를 추가하지 않는다.

**검증:** 승리/패배/도전과 숙련 상한 도달 사례에서 실제 확정 보상과 일치한다. 계측이 추가되면 이탈 시 폐기·오버힐 제외 등 필요한 규칙만 테스트한다. 한국어·영어·일본어 문구 적용.

## REV-08 — 모바일 전투 가독성과 성능 실측

**근거와 불확실성:** `PhaserGame.tsx`는 1600×720 FIT 전장이고 HUD는 최대 7종을 표시한다. 작은 화면에서 병력·위험 경고의 판독 가능성은 코드만으로 판단할 수 없다. 효과 풀과 HUD 100 ms 갱신 제한이 이미 있으므로 성능 개선 필요성을 먼저 측정한다.

**작업:** 360×800, 390×844, 가로 모바일, 데스크톱에서 4/7종 편성, 대형 도전 보스, 지면 경고, 집결 클릭을 확인한다. 언어는 KO/EN/JA, 텍스트 확대도 포함한다. 실제 기기와 브라우저, 1×/1.5×, 측정 구간을 명시하고 프레임 시간·긴 프레임·메모리 추이를 기록한다.

**완료 조건:** 주요 버튼과 경고가 가려지지 않고 집결 클릭이 실제 전장 좌표에 대응한다. 장시간 증원과 전투 재입장 반복에서 지속적인 객체/리스너 증가가 없다. 문제가 확인되면 측정 기반의 합의된 성능 예산과 전후 결과를 남긴다. 증거 없이 렌더러 교체나 대규모 최적화를 하지 않는다.

**제약:** 전장 수치·충돌·적 상한을 화면 개선 때문에 바꾸지 않는다. 스크린샷/CSS 모양 테스트를 늘리지 않고 브라우저 검증 기록을 남긴다. 새 에셋은 현재 아트 계약을 지킨다.

## REV-09 — 실제 진행 경로 기반 밸런스 검증

**문제와 근거:** `scripts/progression-power.test.ts`는 1~8장, 코어 4종, 한 장비 집중 투자, 반복/업적/숙련 제외 모델이다. 절대 적 위협도와 이 모델의 통과는 다양한 편성의 실제 클리어 난이도를 보장하지 않는다. `BALANCE.md`도 이 한계를 명시한다.

**작업:** 균형 투자, 한 병종 집중, 영웅·성채 투자, 제한된 반복 파밍 경로를 구분한다. 6→7, 9→10→11, 12→13, 24→25, 30→도전 구간을 우선 관찰한다. 보석은 출석과 업적을 분리하고 속도/편성 허가에 접근하는 시점을 기록한다. 자동 전투 모델을 추가한다면 실제 엔진과의 차이를 밝힌다.

**완료 조건:** 클리어 시간, 패배 횟수, 지출·잔고, 반복 횟수, 대공 수단과 조작 전략을 포함한 재현 가능한 기록을 남긴다. 기존 모델과 다른 결론은 실측 근거로 설명한다. 문제 구간이 입증되기 전에는 보상·HP·증원 수치를 바꾸지 않는다.

**검증:** 기존 `yarn balance` 임계값은 유지한다. 실제 조정 시 공유 병종·상위 등급 체력 하한·한정 전설 증원 금지 등 계약을 보존하고 BALANCE/GAME_SPEC 및 최소 회귀 테스트를 함께 갱신한다. 계정·결제·원격 분석 서비스는 범위 밖이다.

## REV-10 — 명세와 실제 출력의 불일치 정리

**확인한 사례:**

- README는 영웅 부활을 성채 ‘앞’이라고 설명하지만 `BattleScene`은 `fortressRearSpawnX()`를 사용한다. 같은 README의 다른 문단은 뒤쪽 출전을 올바르게 설명한다.
- `GAME_SPEC.md` §14의 saveCrypto 경로 설명은 password-based지만 현재 export는 앱 관리형 무암호 입력 방식이며 비밀번호는 구형 import에만 필요하다.
- `BALANCE.md` 집중 강화 표는 1~6장이고 일부 수치가 현재 출력과 다르다. 예: 2장 상대 압력 표 357.1/출력 377.2, 4장 456.6/463.6. 현재 검사는 1~8장이다.
- `GAME_SPEC.md` 플레이 루프의 일반적인 ‘성채 또는 보스’ 문구는 캠페인 보스의 두 목표 모두 파괴 조건을 정확히 요약하지 못한다.

**작업과 완료 조건:** 현재 코드와 명령 출력을 기준으로 문서를 정정하고 다른 중복 요약도 확인한다. 문서를 맞추려고 코드를 과거 수치로 되돌리지 않는다. BALANCE의 표는 출력 재현 방법과 범위를 명확히 한다. 이번 리뷰 문서 작성은 이러한 정정의 완료를 의미하지 않는다.

**검증:** 관련 함수·실제 출력과 대조한 문서 diff. 정적 문구마다 테스트를 만들지 않는다. 수치 자체를 변경하는 작업과 분리한다.

## REV-11 — 화면·전투 책임의 점진적 분리

**근거:** 검토 시 `App.tsx` 1,542줄, `BattleScene.ts` 1,826줄에 여러 책임이 모여 있다. 줄 수만으로 결함이라고 단정하지 않지만 저장·화면·전투 변경이 같은 파일에 겹친다.

**작업:** 기능 작업에서 자주 수정하는 화면부터 파일로 추출하고 App은 탐색과 화면 조합을 담당하게 한다. 전투는 순수 판정과 시각효과 수명 관리처럼 경계가 분명한 부분만 분리한다. 추출과 밸런스 변경을 같은 변경에 섞지 않는다.

**완료 조건:** React/Phaser/Zustand의 기존 소유권과 lazy 청크 경계 유지. 전투 결과·이탈 이벤트가 중복 구독되지 않고 재진입 시 정리된다. 데이터 정의를 UI나 새로운 복제 테이블로 이동하지 않는다. 전체 재작성 없이 독립적으로 검토 가능한 단위로 진행한다.

**검증:** 기존 테스트·lint·build와 추출한 화면의 대표 플레이 흐름 확인. 새 테스트는 새로 발견한 회귀 위험에만 추가한다.
